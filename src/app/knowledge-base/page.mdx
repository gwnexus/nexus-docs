# Knowledge Base

The persistent, searchable knowledge store for your project. {{ className: 'lead' }}

The knowledge base holds all durable project knowledge: sessions, decisions, tasks, research notes, and ingested documents. It supports keyword search across all entity types, plus semantic and hybrid search when the server has embeddings enabled.

## What goes in the knowledge base?

The knowledge base is the single source of truth for a project's accumulated knowledge. It stores both structured entities (created through workflows) and unstructured documents (ingested manually or by agents).

**Structured entities** are created through Nexus workflows:
- **Sessions** — execution history with append-only entries
- **ADRs** — architectural decisions with full lifecycle
- **Tasks** — work items with status and notes
- **Dispatches** — coordination records between agents and projects

**Unstructured content** is ingested via the `doc_*` tools:
- Research notes and analysis
- Reference material
- Scan reports (auto-ingested from security and performance scans)
- Planning items

## Entity types

| Entity type | Description | Created by |
| --- | --- | --- |
| `session` | Execution history log | `session_create` |
| `decision` | Architecture Decision Record | `adr_create` |
| `task` | Work item with status tracking | `task_create` |
| `letter` | Dispatch / coordination record | `dispatch_create` |
| `research_note` | Durable technical analysis | `doc_ingest` + classify |
| `planning_item` | Strategic upcoming work | `doc_ingest` + classify |
| `ingest_item` | Raw ingested document | `doc_ingest` |

## Searching

Use `kb_search` with three search modes:

| Mode | Availability |
| --- | --- |
| `keyword` | Always. |
| `hybrid` | Keyword plus semantic results when the server has embeddings enabled; otherwise keyword results with a `warning` field. |
| `semantic` | Only when the server has embeddings enabled; otherwise the call answers 400. |

Since v0.18.2 embeddings are off unless the operator enables them (see [Embeddings on the server](#embeddings-on-the-server)). The dashboard search falls back to keyword matches in the same way.

### Keyword search

Fast, exact matching using full-text search:

```json
{
  "tool": "kb_search",
  "query": "RLS policy",
  "project_id": "...",
  "search_mode": "keyword"
}
```

### Semantic search

Meaning-based retrieval over embeddings. Needs embeddings enabled on the server:

```json
{
  "tool": "kb_search",
  "query": "how do we handle authorization?",
  "project_id": "...",
  "search_mode": "semantic"
}
```

### Hybrid search

Combines keyword and semantic search. Without embeddings it returns the keyword results and a `warning`:

```json
{
  "tool": "kb_search",
  "query": "dispatch routing architecture",
  "project_id": "...",
  "search_mode": "hybrid",
  "entity_types": ["decision", "session"]
}
```

### Related entities

Use `kb_related` to navigate the knowledge graph — find entities related to a given item:

```json
{
  "tool": "kb_related",
  "entity_type": "decision",
  "entity_id": "..."
}
```

## Embeddings on the server

Semantic and hybrid search need embeddings. Since v0.18.2 Nexus sends **no content to OpenAI by default**: a server embeds with OpenAI only when the operator sets both variables:

| Variable | Meaning |
| --- | --- |
| `EMBEDDING_OPENAI_ENABLED` | `true` switches OpenAI embeddings on. Any other value, or no value, keeps them off. |
| `NEXUS_SEC_OPENAI_API_KEY` | The OpenAI API key. A key alone no longer enables embeddings. |

While the switch is off, nothing is embedded, `hybrid` returns keyword results with a `warning`, `semantic` answers 400, and the embedding backfill (`make embed-backfill`) refuses to run.

When the switch is on, Nexus sends the text of these items to OpenAI as they are written: session entries, ADRs, documents (including text extracted from uploads), ingest items and scan reports. Semantic and hybrid search queries are sent as well.

Projects whose [confidentiality level](/confidentiality) blocks external APIs never send content or queries to OpenAI (ADR-0047). They use the local embedding model when the server has one configured; without one, their content is not embedded, `semantic` answers 400 and `hybrid` returns keyword results only.

If the embedding provider fails during a search, `semantic` answers a JSON 503 with a reference and `hybrid` returns the keyword results with a `warning` (v0.18.1).

## Document ingestion

Push content into the knowledge base via `doc_ingest`:

```json
{
  "tool": "doc_ingest",
  "project_id": "...",
  "title": "API rate limiting analysis",
  "body": "## Findings\n\n...",
  "source": "research"
}
```

Documents start as `unclassified` and can be promoted to a specific classification.

## Classification

Ingested documents can be classified to improve search relevance and organization:

| Classification | Purpose |
| --- | --- |
| `unclassified` | Default state for new ingests |
| `research_note` | Durable technical analysis or findings |
| `planning_item` | Strategic work or requirements |
| `decision_input` | Input material for ADR decisions |
| `reference` | Reference documentation |
| `archive` | Historical, no longer active |

## MCP tools

| Tool | Description |
| --- | --- |
| `kb_search` | Keyword search; semantic or hybrid when the server has embeddings enabled |
| `kb_memory` | Structured project memory snapshot |
| `kb_get` | Retrieve a specific entity by type and ID |
| `kb_related` | Find related entities in the knowledge graph |
| `doc_ingest` | Push content into the knowledge base |
| `doc_list` | List ingested documents |
| `doc_classify` | Update document classification |
| `doc_update` | Update document title, body, or URL |
| `doc_delete` | Delete an ingested document |

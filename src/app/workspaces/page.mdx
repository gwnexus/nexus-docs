# Workspaces

Reproducible, version-controlled development environments using Devbox. {{ className: 'lead' }}

Nexus Workspaces follow a Blueprint + Fork architecture: admins create global blueprints, and projects receive independent deep-copy forks that can be customized without affecting the source.

In short: a **blueprint** describes the environment, the project's **fork** is its copy of it, and **your machine** gets the fork with `nexus pull` (and sends changes back with `nexus push`). In Devbox mode the environment is a set of pinned Nix packages: `devbox shell` opens it, `devbox run <script>` runs one of its commands. The project's workspace page explains the same steps under "How workspaces work".

## Blueprint + Fork architecture

A **Workspace Blueprint** is a global template that defines a complete dev environment. It combines:

- A **baseline** — core packages like Go, Node, or Python
- A **flavor** — curated package sets like `nexus-dev` or `web-frontend`
- Optional **post-init scripts** and **metadata variables**

When assigned to a project, Nexus creates a **Fork** — a deep copy of the blueprint at its current version. Forks are fully independent: changes to the composed body, post-init script, or meta variables do not propagate back to the blueprint.

### Wizard

Creating a blueprint uses a 5-step wizard:

1. **Type** — Devbox 0.17 (Dev Containers and devenv coming soon)
2. **Baseline** — core language runtime
3. **Flavor** — curated package bundle
4. **Post-Init Script** — setup commands
5. **Metadata** — project-level variables

Blueprints can be activated, deactivated, or archived. Only active blueprints appear in the project assignment modal.

## Assigning a workspace to a project

Pick the workspace blueprint in the project form, both when creating and when editing a project (v0.16.1):

- **Create:** the chosen blueprint is forked for the new project.
- **Edit:** the picker preselects the blueprint of the project's active fork. Choosing a **different** blueprint forks it on save and archives the previous fork. Keeping the blueprint, or choosing no workspace, leaves the current fork unchanged.
- The picker stays disabled until the current fork has been read; if that fails, it stays disabled with a hint.

If the new fork cannot be created, Nexus tries to restore the archived fork. If that also fails, activate the archived fork again on the project's workspace page.

## Access

Workspace access follows the project roles:

| Role | View forks (scripts, meta variables) | Create, edit, activate, sync, export or delete forks |
| --- | --- | --- |
| Project member (viewer) | Yes | No |
| Project editor or admin | Yes | Yes |
| Platform admin | Yes | Yes |

This applies to the dashboard and to the workspace fork REST API, matching the role check of the MCP `ws_push` tool. Forks contain the devbox scripts that `nexus pull` writes to developer machines, so only editors and admins can change them.

## Baselines and flavors

Baselines provide the foundation packages. Flavors add curated tool sets on top. Both are admin-seeded and read-only.

| Type | Examples | Purpose |
| --- | --- | --- |
| Baseline | `go-1.23`, `node-22`, `python-3.12` | Core language runtime |
| Flavor | `nexus-dev`, `web-frontend`, `data-science` | Curated package bundle |

## Devbox shell (v0.17.0)

v0.17.0 refines the Nexus flavors and blueprints. Changed blueprints get a new version, so their forks show "upstream changed"; use **Review & sync** and then `nexus pull` to take the changes.

- **No `NODE_ENV`:** no flavor or blueprint exports `NODE_ENV` any more. With `NODE_ENV=development`, `next build` failed while prerendering. If your own shell profile sets it, unset it before building.
- **npm commands:** the npm-based Nexus flavors run `dev`, `build`, `lint`, `test` and `typecheck` through `npm run --if-present` and include `netlify-cli`.
- **No tmux:** the Nexus flavors drop tmux and tmuxp, and the `tmux-2w` / `tmux-3w` commands are gone; Zellij is the agent workspace (see [Claude Code Workspace](/claude-code/workspace)).
- **gitleaks** is pinned to 8.30.1, the same version CI uses.
- **Compact summary:** `devbox shell` prints one summary line plus warnings and failures only; set `DBX_VERBOSE=1` to see every check. Optional tools and an unset `ANTHROPIC_API_KEY` (expected with a Claude subscription) are shown as info. A **Commands** block lists every `devbox.json` script with its command.
- **Plugin variables from one source:** every composed `devbox.json` starts its `init_hook` by loading `.nexus/plugin.env`, which `nexus pull` writes from the project's plugin settings (nexus-cli 0.28.11 or later). The flavors no longer copy `HEADROOM_*` values. A missing file is skipped, so projects without plugin variables and older CLIs keep working. A `plugin-env` row in the summary reports the file.

## CLI integration

The Nexus CLI pulls workspace forks and materializes them as local Devbox configuration files:

| Command | Description |
| --- | --- |
| `nexus pull --scope workspace` | Download the active workspace fork and write `devbox.json` + init scripts |
| `nexus status` | Shows workspace fork status including upstream change detection, and the devbox shell state (`[devbox shell: active]`, `inactive`, or active for another project) |
| `nexus pull --dry-run` | Preview workspace changes (create, update, kept files, removals) without writing anything; nexus-cli 0.28.11 or later |

### Files written by nexus pull

`nexus pull` writes or updates the following files in the `.nexus/` workspace cache:

| File | Description | Git-tracked |
| --- | --- | --- |
| `AGENTS.md` | Auto-generated agent identity and role definition | No |
| `CLAUDE.md` | Claude-specific agent context and cross-reference | No |
| `skills/*.md` | Cached skill files for offline reference and IDE autocompletion | No |
| `.nexus/env` | Plugin configuration vars (`HEADROOM_*`, etc.) — non-sensitive, fully overwritten on every pull | No |
| `.nexus/plugin.env` | The same plugin vars as a dotenv file (`KEY=value`) for the devbox `init_hook`; removed when the project has no plugin variables (0.28.11) | No |
| `opencode.json` | MCP server config, plugin assignments, and Headroom MCP block | Project-dependent |

`.nexus/env` is the platform-managed source for all OpenCode plugin environment
variables. It is git-ignored and must never be edited manually — changes in the
Nexus dashboard propagate here on the next `nexus pull`. Use
[`nexus run`](/cli#nexus-run) to launch OpenCode with these vars automatically
injected into the child process.

## devbox.json reference

The `devbox.json` file is the heart of every Nexus workspace. It defines a reproducible, Nix-based development environment.

```json
{
  "packages": [],
  "env": {},
  "shell": {
    "init_hook": [],
    "scripts": {}
  },
  "include": []
}
```

### Key sections

<Properties>
  <Property name="packages" type="array | object">
    Nix packages. Supports version pinning (`go@1.23`), flake references, and per-platform filtering.
  </Property>
  <Property name="env" type="object">
    Environment variables set inside the Devbox shell. Supports `$PWD` and `$PATH`.
  </Property>
  <Property name="shell.init_hook" type="array">
    Shell commands run before every `devbox shell` or `devbox run`.
  </Property>
  <Property name="shell.scripts" type="object">
    Named commands runnable via `devbox run <name>`.
  </Property>
  <Property name="include" type="array">
    References to Devbox plugins (GitHub repos, local paths, or built-in).
  </Property>
</Properties>

### Best practices

- Pin package versions explicitly (e.g. `node@22` instead of `node@latest`) for reproducible builds
- Keep `init_hook` fast — move long-running setup into named scripts
- Use `env` for project-specific config; use `.env` files for secrets
- Use Nexus Meta Variables (`C_DBX_*`) to inject project-level config at fork level

### Files the workspace no longer contains

Since nexus-cli 0.28.11, `nexus pull` cleans up workspace files (`devbox.json`, `scripts/devbox/**`) that an earlier pull wrote but the fork no longer contains:

| Local state | `nexus pull` | `nexus status` |
| --- | --- | --- |
| Unchanged | Deletes the file (`REMOVE`), and empty parent folders | `ORPHANED`: the next pull removes it |
| Modified | Keeps it (`KEEP ... modified, no longer in the workspace`) | `DROPPED`: delete it, or `nexus push <path>` to add it back |

Files that pull never wrote are not touched. Since 0.28.13, `nexus push` skips `DROPPED` files instead of bringing them back into the new fork, unless you name the path.

### Generated scripts and your own scripts

`scripts/devbox/dbx_init.sh`, `dbx_post_init.sh`, `lib/common.sh` and `ops/{check-local,sec-scan,validate}.sh` are generated by Nexus for every workspace on every pull (NEXUS-APP 0.17.1). They are never pushed; nexus-cli 0.29.0 reports a local edit as `DRIFTED`. Put your own steps into `scripts/devbox/init/os_<os>/override.sh` or into an own script, and use `nexus reset <path>` to restore a generated one.

Since NEXUS-APP 0.18.0:

- The ops scripts fail again: `check-local.sh` exits 1 when a required tool is missing, `validate.sh` checks `package.json`, `devbox.json` and every devbox script (`bash -n`) and exits 1 on problems, and `sec-scan.sh` runs gitleaks (a pattern scan of tracked files as fallback) and exits 1 on findings.
- Forks created before 0.17.0 still store comment-only `init/os_<os>/override.sh` placeholders; `nexus pull` no longer delivers them and removes the local copies. Overrides with real commands stay.

Run `nexus pull` to get the new scripts.

### Validation

The Nexus workspace editor validates `devbox.json` in real-time: JSON syntax errors are caught immediately, and devbox-specific rules (valid top-level keys, package format, platform names, shell structure) are checked before saving.

## Upstream change detection

When a blueprint is updated after a fork has been created, a database trigger sets `upstream_changed = true` on all forks of that blueprint. This flag is visible in both the UI and the CLI, letting project teams decide when to pull the latest changes.

Since v0.17.0, the "upstream blueprint changed" notice on the project's workspace page names the fork and both versions, explains the 3-way merge and offers **Review & sync** (opens the merge preview). The sync dialog reminds you to run `nexus pull` afterwards. Forks created before snapshots existed now merge against the blueprint version they are based on, so a sync updates their files instead of only advancing the version. Since v0.17.2, forks in shadow mode keep getting the notice; the "Ignore & decouple" action is removed.

## Per-key fork sync

Since v0.18.0, a sync merges the fork's `devbox.json` body and its meta variables **key by key** against the blueprint version the fork is based on:

| Key changed by | Result |
| --- | --- |
| Blueprint only (or nobody) | The fork takes the blueprint value, removals included. |
| Fork only (added or changed) | The fork keeps its value. |
| Both | The fork keeps its value; the key is reported as a **conflict** in the sync dialog and the sync API. |

Before 0.18.0, one customized key kept the whole `devbox.json`, so customized forks missed every blueprint fix. Review the reported conflicts after a sync and adopt the blueprint value by hand where you want it.

Platform operators can sync every active fork of an environment at once with `scripts/sync-workspace-forks.ts` in nexus-app: a dry run by default, `--apply` writes after a JSON backup. As with the dashboard sync, every listed fork advances its base version and loses the upstream flag, also when it takes no value.

## Shadowed workspaces

A project can keep its devbox workspace out of git with the project setting `policy.shadow_workspace`, or through the shadow level `ai` / `nexus`. Shadowed projects get a shadow-safe `dbx_init.sh` and `devbox.json` without AI tooling. See [Workspace shadow](/project-settings#workspace-shadow).

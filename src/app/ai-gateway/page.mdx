# AI Gateway

Bring your own provider keys, browse a curated model registry, evaluate routing suitability with evidence, and operate the gateway with a live decision trail. {{ className: 'lead' }}

<Note>
  **Planned, not yet available to users.** Availability will be announced after provider-key verification and release checks are complete. Since 0.18.0 the AI Gateway is held back: the sidebar entry is grayed out with a note, and `/dashboard/ai-gateway` redirects to the dashboard for everyone but the platform owner. NEXUS-APP 0.20.0 and 0.21.0 do not change this; 0.21.0 connects [AI Hardware nodes](/nexus-link#model-routing) to model routing for platform admins. This page describes the planned scope.
</Note>

Introduced across the v0.13.n release line, the AI Gateway groups the provider-credential, model-catalog, routing-suitability, and operations tooling that sits behind projects running in `execution_mode = nexus_gateway`.

## Overview

The AI Gateway is made up of four cooperating parts:

| Area | Version | Purpose |
| --- | --- | --- |
| BYOK / Provider Credentials | v0.13.1 | Bring your own OpenRouter, Anthropic, or OpenCode Zen key; bind projects to a specific credential |
| Model Catalog Rebuild | v0.13.2 | Registry (curated, routable) vs. Discover (raw upstream feed) split |
| Routing Lab | v0.13.3 | Evidence-based model suitability scoring for scenario recommendations |
| Gateway Operations | v0.13.4 | Route simulation, decision audit trail, and cost reconciliation |

## BYOK: provider credentials

Under **Settings → Provider Keys**, a user can add their own API key for a supported provider:

- OpenRouter
- Anthropic
- OpenCode Zen

Keys are encrypted at rest and non-destructively verified against the provider's own key-info endpoint before being accepted -- no test request is made against a billable model endpoint.

Projects running in `execution_mode = nexus_gateway` now carry an explicit, audited **billing binding**: a record of which credential the project draws from. Previously this was inferred from whoever created the project's runtime token; it is now a first-class, auditable relationship.

Relevant surface:

- UI: Settings → Provider Keys (`provider-credentials-manager`), add-key form
- API: `POST /api/user-credentials`, `PATCH /api/projects/[projectId]/provider-binding`

See ADR-0096 for the credential model and audit requirements.

## Model catalog: Registry and Discover

<Note>
  "Catalog" as a standalone term is now ambiguous. As of v0.13.2, the AI Gateway catalog tab is split into two distinct views: **Registry** and **Discover**.
</Note>

- **Registry** -- the curated set of Nexus-admitted models. Only Registry models are routable by actors and route aliases.
- **Discover** -- the full raw feed pulled from OpenRouter and models.dev, used to browse and pull in new candidate models.

A nightly `pg_cron` job syncs the OpenRouter and models.dev catalogs directly into Postgres. OpenCode Zen is now a first-class aggregator alongside OpenRouter.

### Catalog drift log

Upstream changes to price, alias, or context-length on models backing an **active** deployment are recorded in a drift log before being applied, so operators can review a change before it silently affects cost or capability.

See ADR-0097 (catalog rebuild) and ADR-0100 (Registry/Discover terminology) for the full model.

<Note>
  Existing documentation that refers to a single unified "Model Route catalog" (see [Model Routing](/actors/model-routing)) predates this split and describes the Registry side specifically. Route aliases resolve against Registry entries only.
</Note>

## Routing Lab: evidence-based suitability

Routing Lab adds an **evidence layer** to model selection. Suitability scores are informed by:

- LiveBench
- LMArena
- Nexus's own scenario fixtures (deterministic and LLM-judged test runs against your configured deployments)

Each evidence source carries a trust/precedence weight (ADR-0104). Scenario-based recommendations present quality, cost, and latency as separate, honestly labeled lenses -- a dimension with no supporting evidence is shown as **missing**, never faked as a zero score.

Relevant surface:

- UI: scenario recommendation panel, evidence sources panel, evidence mappings panel (Platform admin)
- Core logic: suitability scoring, evidence ingest, HTTP/JSON and Hugging Face dataset adapters, judge scoring

## Gateway operations

Three operator-facing tools ship as part of Gateway Operations (v0.13.4):

### Route Simulator

Dry-run a routing profile or scenario against live gateway policy before committing to it. Once a simulated change is actually observed in production routing, a live confirmation banner surfaces to close the loop.

### Immediate policy reload

Since v0.15.0, routing policy changes reach the gateway right away. After a routing policy write (the Route Simulator quick switch or a change to a route policy), the control plane asks the gateway to reload its policy instead of waiting for the regular bundle poll (about 30 seconds). This is best effort: a failed reload never fails the write, the poll remains the fallback, and the simulator's confirmation still checks the policy version (now immediately after a successful reload).

### Route decision audit trail

Every gateway routing decision -- selected deployment, fallback reason, budget state -- is recorded as a queryable, project-scoped history. This history is visible to project members, not only platform admins.

### Cost reconciliation

A platform-admin-only view that compares a provider's own account usage and credit balance (for example, OpenRouter) against Nexus's internal cost ledger, surfacing discrepancies for investigation.

- API: `GET /api/admin/cost-reconciliation`

## Runtime behavior (nexus-gateway 0.3 to 0.6) {{ id: 'runtime-behavior' }}

The gateway service (nexus-gateway) releases 0.3.0 to 0.6.1 change behavior that callers and operators see. All of them require hub 0.21.0. They roll out on staging first; production follows hub 0.21.0.

### Error codes

| Status | Code | Surface | When |
| --- | --- | --- | --- |
| 503 | `policy_stale` | `/v1/chat/completions`, `/v1/messages` (message starts with `policy_stale:`) | The gateway has not reached the hub for `stale_fail_secs` (default 1800 s). Also applies to requests already in flight, before their next upstream attempt. (0.3.0) |
| 503 | `no_eligible_deployment` | `/v1/chat/completions` | No local deployment may serve the request, because of its [reviewed data boundary](#reviewed-data-boundary) or its [advertised surfaces](#advertised-surfaces). (0.4.0) |
| 503 | `api_error` | `/v1/messages` | Same cause as `no_eligible_deployment`, on the Messages API. (0.4.0) |
| 400 | `context_too_long` | `/v1/chat/completions`, `/v1/messages` | The prompt is estimated above the deployment's `max_context_tokens`; refused before any upstream call. Chat completions since 0.5.0. |

The context estimate is about 4 characters per token, over the messages, tool calls and tool definitions.

### Local-model routing

#### Reviewed data boundary

A local deployment is reviewed up to a classification, for example `confidential` (ADR-0149). Since 0.4.0 the gateway never uses it for a request classified above that level.

- If no other local deployment fits, the request fails with 503 (see [Error codes](#error-codes)).
- A local profile or a `@local` variant never falls back to a cloud model.
- The Routing Lab shows the reason `above_max_classification`.

#### Advertised surfaces

Since 0.3.0 (effective with hub bundle schema 1.3), a local deployment serves only the APIs it passed the admission probes for: `chat_completions`, `messages` or both.

Example: a model that passes the chat probes but fails the Messages probes is not offered on `/v1/messages`. A `nexus/<profile>@local` request there gets 503 when no other local model qualifies.

#### Credentials of local deployments

Local deployments (`data_path: local_only`) always use their configured credential, never a project BYOK key. Before 0.6.1, chat requests with a project token to a local deployment could fail with 502 `byok_resolution_unavailable`.

### Output-token cap

When a deployment declares `max_output_tokens` (0.5.0), both inference surfaces apply it:

- a larger client `max_tokens` or `max_completion_tokens` is lowered to the cap, and the cap is set when the client sends none;
- the request is never refused for it;
- a manual thinking budget is kept below the cap, or `thinking` is removed when the cap is under 1024.

Usage events carry `max_tokens_requested` and `max_tokens_applied`; the hub stores them since gateway 0.6.0.

### Usage and decision views

Since 0.3.0 the usage and decision views can show `effective_profile`, the purpose profile behind a variant: `coding` for `coding@local`.

### Messages API responses

Since 0.6.1, `/v1/messages` without `stream` answers with JSON, as the Messages API default. Before, it could answer with an event stream.

### Health and readiness

- `/health/ready` reports a stale routing policy (0.3.0). `/v1/models` keeps answering while the policy is stale.
- Since 0.6.0 it also reports the current bundle:

  | Field | Meaning |
  | --- | --- |
  | `bundle_version` | The hub's canonical content hash of the bundle, also its ETag. |
  | `bundle_schema_version` | Schema of the bundle, for example `"1.3"`. |
  | `bundle_accepted_at` | When the current bundle content was accepted (RFC 3339, UTC). |

<Note>
  **Alert on readiness.** A hub outage longer than `stale_fail_secs` (30 minutes by default) stops inference with `policy_stale`. Watch `/health/ready`, not only liveness.
</Note>

## Security and data-integrity hardening

v0.13.5 shipped a set of internal hardening changes alongside the gateway features above: consistent `apiError()` responses, atomic credential/skill/evidence writes, outbound request timeouts, a cache-invalidation race fix, closing a project re-parenting authorization gap, and a compliance-jurisdiction fix for OpenRouter-routed vendor/model IDs. These are operational improvements with no direct user-facing surface.

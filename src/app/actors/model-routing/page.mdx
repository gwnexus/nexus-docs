# Model Routing

Actors choose their model through a Model Profile; the gateway picks the concrete model. {{ className: 'lead' }}

<Note>
  Since v0.21.0 actors route **only** through their Model Profile. Legacy route aliases (`route_alias`) were bound to profiles and removed. Earlier versions of this page described the route alias catalog; see [Migration from route aliases](#migration-from-route-aliases).
</Note>

## Model Profiles

A Model Profile is a stable name for a kind of work, for example `reasoning`, `coding` or `review`. An actor references a profile instead of a provider model ID, so a provider renaming or retiring a model does not touch any actor.

The actor edit page has one **Model** field: the Model Profile. The gateway resolves the profile to a concrete model, in the cloud or on your own [AI hardware](/nexus-link#model-routing). The actor tabs are named Persona, Capabilities & Dispatch and Advanced runtime.

Only active profiles count. A binding to an inactive profile is treated like no binding.

## Where a profile applies

| Project execution | What the actor runs on |
| --- | --- |
| Through the gateway (`execution_mode = nexus_gateway`) | The actor's Model Profile; OpenCode exports write `nexus/<profile-slug>`. |
| Outside the gateway (`direct_provider`) | A profile does not apply; the actor runs on the project default. |
| No profile bound | The project or runtime default. |

The [AI Gateway](/ai-gateway) itself is not yet available to users, so most projects run outside the gateway and their actors use the project default.

## Actor routing configuration

An actor file names its profile under `routing`:

```yaml
routing:
  model_profile: coding
```

Actor downloads from the dashboard write `routing.model_profile` (0.21.0). The runtime spec no longer carries `route_alias` per actor.

## Imports and downloads

Actor imports accept both `model_profile` and a legacy `route_alias` and bind either to an active profile, with the same rule as the migration below. Names without an active profile are listed in `unbound_profiles` in the import result; those actors run on the project default until you choose a profile.

nexus-cli releases after 0.42.0 read `model_profile` at the top level or under `routing` in `nexus actors import`, `normalize` and `validate`, so a re-imported download keeps its profile; `validate` reports a `route_alias` as legacy.

## Migration from route aliases

Migration 0318 (v0.21.0) bound every actor that still used a legacy route alias to a Model Profile:

1. `balanced-reasoning`, `balanced-coding` and `balanced-review` map to `reasoning`, `coding` and `review`; every other alias maps to the profile with the same slug.
2. The actor's tenant profile is used first, then the global profile; only active profiles count.
3. Actors without a match run on the project default.

The migration removed the alias together with the provider, model, fallback and local flag that the old route picker wrote next to it. Every change is recorded in `actor_route_alias_migration` for review and rollback.

Also removed in v0.21.0:

- the "Legacy model route" picker on the actor page;
- the alias fallback in the OpenCode and Claude Code exports;
- the 422 for an unknown alias.

## Local models

Local models run through the gateway, as deployments on your [AI hardware](/nexus-link#model-routing). v0.21.0 removed the legacy "Local models" (DGX Spark) section of the project form and its direct `dgx-spark` provider in the OpenCode export. Projects that still carry `spark_models` get the export warning `legacy_local_models`.

A local deployment serves only requests up to its reviewed classification and only the APIs it passed admission for; a local profile never falls back to a cloud model. See [AI Gateway: local-model routing](/ai-gateway#local-model-routing).

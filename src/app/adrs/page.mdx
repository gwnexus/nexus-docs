# Architecture Decision Records

Formal, versioned records of technical decisions made within a project. {{ className: 'lead' }}

ADRs capture the context, decision, and consequences of significant technical or architectural choices. They are the durable decision log for your project — searchable, reviewable, and auditable.

## What is an ADR?

An ADR (Architecture Decision Record) documents a technical or architectural decision that affects the project. Unlike session notes, ADRs are **permanent** — they represent decisions that should be understood and respected by all future agents and team members.

ADRs are first-class entities in Nexus with a formal review lifecycle. They are searchable via `kb_search` and surface automatically in agent context at session start via `kb_memory`.

## ADR lifecycle

```
draft -> under_review -> accepted / rejected
              |              |
              v              v
        draft (changes   deprecated (0.21.0)
         requested)
```

| Status | Description |
| --- | --- |
| `draft` | Initial state. The ADR is being written and refined. |
| `under_review` | Submitted for team review. Comments can be added via `dc_add`. |
| `accepted` | The decision is approved and becomes authoritative. "Accepted with conditions" (0.21.0) is also status `accepted`, with the conditions in the ADR text. |
| `rejected` | The decision was not approved. Preserved for historical context. |
| `deprecated` | Since 0.21.0: an accepted ADR that no longer applies, retired by a reviewer without a successor. |
| `superseded` | Replaced by a newer ADR. Automatically set when the superseding ADR is accepted, or set by a reviewer with "Confirm supersession and close" (since 0.20.0, see [Supersession](#supersession)). |

### Governance widget (0.20.0)

On the ADR page, the Governance widget is one row of fixed height: the steps Draft, Under review and Decision, one status line and the actions. Submit, accept and reject (with a rationale) open in a drawer on the right. The confirm button stays locked from the click until the page shows the new state, and every transition is conditional on the expected state: a double click or a concurrent call gets a conflict instead of a second transition. Reject stays available under review.

Authors cannot vote on their own ADR: the API rejects it, the widget explains why, and a database trigger blocks it. Self votes cast before 0.20.0 were deleted.

## Review decisions

Since 0.21.0, **Review** on an ADR under review opens the drawer on the right with a decision dropdown:

| Decision | Effect |
| --- | --- |
| **Accept** | Status `accepted`; the rationale is appended as `## Decision Rationale`. |
| **Accept with conditions** | Status `accepted`; the conditions are appended as `## Conditions`. |
| **Request changes** | Back to `draft`; the reason is posted as a comment. The author revises and submits again. |
| **Reject** | Status `rejected`, with an optional reason: alternative preferred, insufficient context or evidence, out of scope, duplicate, obsolete. |

Review texts (rationale, conditions) are plain text of at most 10,000 characters, in the dashboard and through MCP; other input gets a 400. Every decision is conditional on the state that was read: a concurrent decision gets 409 instead of overwriting the first. Each decision notifies the project members (see [Notifications](/notifications)).

## Change requests

**Request change** on an accepted ADR offers three kinds:

| Kind | Effect |
| --- | --- |
| **Revision** | A new draft that supersedes the ADR opens in the editor. |
| **Amendment** | Same as a revision, for an addition rather than a rework. |
| **Deprecation** | The ADR moves from `accepted` to `deprecated`. Reviewers only (`decisions.accept`). |

Revisions and amendments follow the normal lifecycle; accepting the new ADR marks the old one `superseded` (see [Supersession](#supersession)). The earlier change-request page redirects to the ADR.

## Review history

The ADR list shows the review path under each title, for example "Submitted for review -> Changes requested", and a badge next to the status for what matters now:

| Badge | Meaning |
| --- | --- |
| **With conditions** | Accepted with conditions; the conditions show as tooltip. |
| **Changes requested** | A draft sent back by a reviewer. |
| **Resubmitted (round n)** | Submitted again after changes were requested. |
| **Change requested** | An accepted ADR with an open change request. |

The ADR page shows the conditions or the requested changes in a highlighted box and the full review history with actor, time and reason. The history is recorded since 0.21.0; earlier decisions show no path.

## ADR overview

The status quick filters on the ADR overview are always visible, including **Needs my review** (under review, decidable by you, not your own) and **Deprecated**. Select ADRs to download them as Markdown; several download as one zip (`decisions.read`, audit event `decisions.exported`).

## ADR structure

Every ADR follows a standard format:

<Properties>
  <Property name="Title" type="string">
    Short, descriptive. Format: "Use X for Y" or "Adopt X over Y".
  </Property>
  <Property name="Context" type="markdown">
    What is the situation? What problem are we solving? What constraints exist? What alternatives were considered?
  </Property>
  <Property name="Decision" type="markdown">
    What is the decision? Stated clearly and directly. Includes key implementation details that affect the architecture.
  </Property>
  <Property name="Consequences" type="markdown">
    Expected positive outcomes, known trade-offs or risks, follow-up work required.
  </Property>
</Properties>

## Creating an ADR

Use the `/nexus-adr-draft` skill for guided ADR creation:

```
/nexus-adr-draft
```

Or create directly via MCP tools:

```json
{
  "tool": "adr_create",
  "project_id": "...",
  "title": "Use Supabase RLS for row-level access control",
  "context": "We need to enforce data isolation...",
  "decision": "We will use Supabase Row Level Security...",
  "consequences": "Positive: automatic enforcement at the DB layer..."
}
```

After drafting, submit for review:

```json
{
  "tool": "adr_submit",
  "adr_id": "..."
}
```

## Supersession

When a new ADR replaces an existing one, specify the `supersedes` field during creation. Since 0.21.0 the superseded ADR must belong to the same project (dashboard and `adr_create`; otherwise 400). When the new ADR is accepted, the superseded ADR is automatically marked as `superseded`.

Since 0.20.0 an ADR that another **open** ADR supersedes is locked: it can no longer be submitted or accepted, neither in the dashboard nor with `adr_submit` or `adr_decide`, and the widget links the superseding ADR. Its exit is **Confirm supersession and close**: a reviewer closes it as superseded from draft or under review. The closure note goes into the decision text in the same update, plus a comment; if the decision text was edited meanwhile, the close answers 409 instead of overwriting it.

```json
{
  "tool": "adr_decide",
  "adr_id": "...",
  "decision": "superseded"
}
```

The dashboard action is `close_superseded`. Both need `decisions.accept` (`project_admin` or `project_reviewer`).

Use `kb_related` to navigate supersession chains and understand the evolution of decisions.

## MCP tools

| Tool | Description |
| --- | --- |
| `adr_create` | Create a new ADR in draft status |
| `adr_submit` | Submit a draft ADR for review; a concurrent second submit gets 409 (0.21.0) |
| `adr_decide` | Decide an ADR, see the decisions below |
| `dc_add` | Add a comment to an ADR under review |
| `dc_list` | List comments on an ADR |

`adr_decide` takes these decisions:

| `decision` | Applies to | Extra fields |
| --- | --- | --- |
| `accepted` | under review | optional `rationale` |
| `accepted_with_conditions` (0.21.0) | under review | `conditions` (required) |
| `changes_requested` (0.21.0) | under review | `rationale` (required); back to draft, posted as a comment |
| `rejected` | under review | optional `rationale`, optional `reason` (0.21.0): `alternative_preferred`, `insufficient_context`, `out_of_scope`, `duplicate`, `obsolete` |
| `deprecated` (0.21.0) | accepted | `rationale` (required) |
| `superseded` (0.20.0) | draft or under review, superseded by an open ADR | optional `rationale` (closure note) |

Since 0.21.0 the dashboard and MCP share one implementation: the appended text, the 409 on a concurrent decision and the notifications are identical. MCP accept and reject now append `## Decision Rationale` like the dashboard (before: `**Review rationale:**`).

Since NEXUS-APP 0.19.1 the ADR tools follow the project role matrix: `adr_create` and `adr_submit` need `project_admin` or `project_editor`, `adr_decide` needs `project_admin` or `project_reviewer` (platform admins pass); other callers get 403. ADR comments need access to the project. See [Permissions on write tools](/mcp-server#permissions-on-write-tools).

# Security and Hardening

The platform-level security controls that protect tenant data, audit integrity, and the deployment pipeline. {{ className: 'lead' }}

This page collects the security posture hardening shipped since v0.12.0, including the tenant isolation and role checks of v0.15.0 to v0.16.1. It complements the confidentiality model ([action gating](/confidentiality) and AI routing) and the [audit and SIEM](/audit-siem) subsystem.

## Access policy scoping

Sensitive tables are scoped to the service role so that they cannot be read or written through the standard request-scoped client.

- `user_feature_flags` — feature-flag grants are managed only through server-side, service-role paths
- `audit_events` — audit records are write-only from application code and never exposed to end-user clients

This prevents privilege escalation via direct table access and keeps the audit trail tamper-resistant.

## Fail-closed guards

Guards default to denying the operation when preconditions are not met.

- **Staging seed guard** — the staging database seed refuses to run unless an explicit target allowlist is provided and the connection is HTTPS. A misconfigured or unexpected target aborts the seed rather than proceeding.

- **Complete directive lists only** (v0.16.0) — when the directive catalog, a project's rules or its settings cannot be read, the agent file export, `pd_list`, `directive_export` and the directives REST endpoint answer 503 with the missing sources instead of returning a list without the platform rules. Agent files are not regenerated from an incomplete list.

<Note>
  Fail-closed means the safe default is to stop. An unset or ambiguous configuration results in denial, not a best-effort attempt.
</Note>

## Tenant isolation (SEC-007)

Database tables must not be readable across tenants through the public data API, even by signed-in users with their own token.

- **v0.15.0:** fourteen tables (including licenses, skill versions, reviews and their comments and participants, workspaces, baselines, flavors, blueprint versions, machines, actors and actor assets) had a permissive read policy for every signed-in user. These policies were dropped; the application reads these tables only through server-side paths, so its behavior did not change.
- **v0.16.0:** eight more tables (tags, entity tags, model routes, runtime and model profiles, provider deployments, route policies and provider subscriptions) followed.
- Both migrations fail if a permissive read policy for signed-in, anonymous or public roles remains afterwards, so the gap cannot silently reopen.

## Role checks

| Area | Since | Rule |
| --- | --- | --- |
| Skills via MCP | v0.16.0 | Core skills: platform admins only. Project skills: project admin or editor. Assigning and unassigning: project admin or editor (before: any member, including viewers). |
| Directives via MCP | v0.16.0 | Create, update and toggle: project admin or editor. Delete: project admin. Update, delete and toggle write audit entries. |
| Workspace forks | v0.16.1 | Viewing forks needs project membership; creating, editing, activating, syncing, exporting or deleting them needs a project admin or editor role. Platform admins keep access. Before, any signed-in user could reach these routes. |
| Skill API | v0.16.3 | `GET /api/skills` and `GET /api/skills/<id>` apply the same visibility as the skill registry pages: global skills for every signed-in user, project skills for project members only. Before, any signed-in user could read project skills of projects they were not a member of. |
| Project actors | v0.17.0 | Saving a project replaces its actor assignments in one transaction, keeps role overrides and rejects actors of another tenant. |
| Agent files via MCP | v0.18.0 | `af_create`, `af_update` and `af_activate` needed only a valid token. Core agent files now need a platform admin, project agent files a project admin or editor, as on the dashboard routes. |
| Project skill export | v0.18.0 | `GET /api/projects/<id>/skills/export` checks project membership for API token callers too. |
| Audit events | v0.18.0 | Non-admins may only record dashboard event types, and the severity is validated, so audit entries cannot be forged. |

See [Workspaces](/workspaces#access) and [Skills](/skills#skill-scope).

## Server-only database functions

Some database functions bypass row level security because only the server and scheduled jobs call them.

- **v0.16.2:** fourteen such functions could still be called with the public API key, for example to replace a project's workspace fork or skill assignments, or to read embeddings. Clients can no longer call them; the server and the scheduler keep running them.
- **v0.17.0:** the price and model sync functions are also scheduler-only.

## Error responses

Since v0.17.0, every server error (5xx) of the API goes through one handler: the client gets a safe message and a **reference**, which is also in the server log and the error tracker. Quote the reference when you report a problem. Error screens in the app show a friendly text, "Try again" and the reference to quote; raw error details appear only outside production.

Provider credentials no longer depend on the user who created them: deleting a user keeps organization and Nexus-managed keys, revokes that user's personal keys, and project bindings to a revoked key fail closed.

## Node calls and DNS rebinding

Since v0.16.0, calls from the control plane to registered AI nodes (compose file, logs and activation) are protected against DNS rebinding. Every address a node hostname resolves to is checked when the connection is made:

- loopback, link-local and cloud metadata addresses are refused
- public names must resolve to public addresses; LAN names may resolve privately
- redirects from a node are no longer followed or passed through; they return 502

## Secret scanning

- **gitleaks pre-commit hook** — runs fail-closed. A commit that would introduce a secret is blocked before it can enter history.

This keeps credentials, tokens, and private keys out of the repository at the earliest possible point.

## Safe export encoding

- **CEF output escaping** — the SIEM CEF export escapes field values on the server so that event data cannot inject or break out of CEF fields in downstream parsers.

See [Audit Log and SIEM](/audit-siem) for the export endpoints and formats.

## Export and path rules (v0.18.0)

What Nexus sends to developer machines is checked on both sides:

- **Executable content needs consent.** `af_export`, `ws_export` and `sk_export` list every runnable item they install (`executables`: kind, id, target path, command, SHA-256; env values never sent). nexus-cli 0.31.0 or later asks before installing a new or changed item. See [Consent for executable content](/cli#consent-for-executable-content).
- **Size cap.** These exports answer `413` above 8 MiB of uncompressed JSON; the CLI refuses larger responses too.
- **Repo-relative paths only.** Agent file target paths, the workspace scripts path, script file names and the agentic root reject `..`, absolute or home paths, backslashes, control characters and anything inside `.git`. nexus-cli 0.29.2 checks the same before every write.
- **Safe names.** Skill ids, command slugs and skill resource file names may only use `[A-Za-z0-9._-]`; exports skip older rows that break the rule.
- **Git settings fail closed.** Invalid fields in a project's Git configuration (for example a written-through `gh` profile) are dropped before they reach the CLI.
- **Downloads never render inline.** Document downloads are always attachments with `Content-Security-Policy: sandbox` and `nosniff`, so uploaded HTML or SVG cannot run script on the app origin.
- **Shadowed repositories** keep the devbox workspace out of git and receive a workspace without AI tooling. See [Workspace shadow](/project-settings#workspace-shadow).
